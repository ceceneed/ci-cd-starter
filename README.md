# CI/CD入门：概念、测试人员视角与GitHub Actions实操

这套示例用一个“满100元减20元”的网页，把提交代码、自动测试、构建和部署连起来。你只需要Node.js 22或以上版本；示例没有第三方依赖，不需要API Key。

建议顺序：先看一、二，再执行三，最后配置四。先跑通一个小项目，再迁移到公司项目。

## 一、先把四个动作分清楚

| 动作 | 在做什么 | 本示例对应内容 |
|---|---|---|
| 提交/合并 | 把代码版本交给Git管理，或把分支修改合入共享分支 | Git提交、PR与合并main |
| 测试 | 检查行为是否符合事先确定的预期 | 100元应付80元的断言 |
| 构建 | 从源代码生成可以发布的文件包 | 把网页和脚本生成到dist/ |
| 部署 | 把文件包交给目标运行环境，让用户可以访问 | 发布到GitHub Pages |

这里的构建只是整理静态文件。真实项目可能还要编译Java、打包前端或生成Docker镜像。构建成功只能说明这一步完成，不能证明业务正确。

### CI：持续集成

开发频繁把小改动合入共享分支，并及时自动构建和测试，尽早发现集成问题。PR在合并前也可以先跑同样的检查。

GitHub Actions负责按照配置执行这些动作。只在电脑上跑一次测试，还没有建立“提交代码就自动检查”的流程。

### CD的两个含义

| 方式 | 达到什么状态 | 谁决定最终发布 |
|---|---|---|
| 持续交付 Continuous Delivery | 通过检查的版本随时可以发布 | 通常保留人工决定 |
| 持续部署 Continuous Deployment | 通过既定检查的修改自动进入生产环境 | 自动规则 |

本示例默认在main更新且检查通过后自动发布到Pages，用于学习持续部署。若在github-pages环境配置必要审批人，部署前就会等待人工批准，可用来体验持续交付。

合并PR的代码审查与部署环境审批是两个不同环节，实际团队可以同时设置。

先自测：代码“构建成功”但100元没有减20元，这个版本能发布吗？答案是不能；需要业务断言发现问题，并把测试结果接到发布条件上。

## 二、测试人员具体参与什么

测试人员不必独自搭建所有基础设施，但需要参与定义“满足哪些条件才能继续”。

| 环节 | 测试人员的工作 | 适合自动化的检查 |
|---|---|---|
| 需求讨论 | 明确规则、边界、失败预期 | 确定99.99、100、100.01元的预期 |
| 提交/PR | 选出执行快、结果稳定的回归检查 | 单元测试、接口契约和核心接口测试 |
| 测试环境 | 验证组件连起来后的关键流程 | 接口集成测试、少量核心UI流程 |
| 发布前 | 评估缺陷、变更范围和剩余风险 | 相关回归；必要的探索、体验和专项测试 |
| 发布后 | 确认服务可用、关键行为正常 | 冒烟检查和监控 |

本例是静态网页，没有后端API；接口测试是迁移到真实系统时可加入的内容。

“冒烟测试”通常指少量、快速检查：系统能否打开，最关键的功能能否工作。它不等于完整回归。

本例的业务边界：

| 订单金额 | 应付金额 | 检查目的 |
|---|---|---|
| 99.99元 | 99.99元 | 门槛前一分不优惠 |
| 100.00元 | 80.00元 | 达到门槛就优惠 |
| 100.01元 | 80.01元 | 超过门槛正常优惠 |
| 200.00元 | 180.00元 | 只减一次20元 |

例如，开发把`>= 100`误写成`> 100`，只测200元就发现不了。100元边界用例才会失败。这说明自动化检查的价值取决于用例和预期，不取决于流水线有多少步骤。

遇到红色失败记录，先读失败步骤、日志和断言，区分业务回归、用例自身问题、测试数据/环境问题、运行器或网络问题。重跑成功也需要判断是否存在偶发失败，不能直接认定产品正确。

## 三、先在本地体验通过与失败

### 1. 打开本示例目录的终端

确认当前目录能看到`package.json`，执行：

```powershell
node --version
npm.cmd run pipeline
```

Windows使用`npm.cmd`可以避开PowerShell对`npm.ps1`的执行策略限制。在macOS/Linux中把`npm.cmd`写成`npm`。

预期最后看到：

```text
[PIPELINE PASS] 测试 → 构建 → 产物检查 → 本地部署 → 部署后检查全部通过。
```

这条命令会运行15个业务测试，生成dist/，检查产物，然后把同一份文件复制到release/模拟本地部署，再检查release/。它用于理解机制；真正的GitHub工作流在后面配置。

### 2. 体验“错误阻止发布”

```powershell
npm.cmd run demo:failure
```

脚本只在隔离副本中把优惠条件从`>=`改成`>`。预期看到：

```text
刚好达到门槛：100元应付80元 → 失败
[PIPELINE STOP] 测试业务规则失败，后续步骤停止，本次不执行部署。
[EXPECTED FAILURE VERIFIED] 边界测试发现错误；构建和部署均未执行；源文件保持正确。
```

注意：副本中的流水线返回非零退出码；演示脚本确认“确实拦住错误”后返回0。演示脚本执行成功，表示失败拦截机制验证成功。

如果旧版本之前已经发布，它会继续存在。某次失败意味着本次没有发布新版本，并不表示自动删除旧版本。

### 3. 打开页面做人工体验

```powershell
npm.cmd run build
npm.cmd start
```

终端会显示本地地址`http://127.0.0.1:4173`。由你在浏览器中打开，输入99.99、100和100.01，检查显示金额；还可以试空值、负数和三位小数。按Ctrl+C停止服务。

若4173端口已占用，请先停止占用该端口的练习服务，或修改`scripts/serve.mjs`中的端口。

## 四、实际配置GitHub Actions

完整配置已经保存在`.github/workflows/ci-cd.yml`。需要把这个目录和源码一起放进GitHub仓库根目录，不能只上传src/。

### 1. 准备学习仓库与Pages

以下是由你在GitHub中进行的操作，本次没有登录、创建远端仓库或上传内容。

1. 新建一个空的学习仓库。为减少Pages套餐差异，入门可选公开仓库。创建时暂不勾选自动生成README、License等文件，避免首次推送产生额外合并步骤。
2. 进入仓库的`Settings → Pages`，在`Build and deployment → Source`中选择`GitHub Actions`。若仓库为空导致暂时不可设置，可以先完成首次推送，再回来设置并重跑失败的部署任务。
3. 若仓库或组织禁用了Actions，需要先由具有权限的人开启相应能力。

GitHub界面的文字可能变化，按Pages、发布来源和Actions这几个功能定位。

### 2. 上传示例

在本示例目录执行以下命令。请把仓库地址占位文字换成你刚创建仓库的实际HTTPS地址；`git push`会上传示例，且main上的通过版本会自动发布页面。

```powershell
git init -b main
git add .
git commit -m "Add CI/CD learning demo"
git remote add origin "替换为你的GitHub仓库HTTPS地址"
git push -u origin main
```

Git首次使用可能要求配置提交姓名、邮箱和完成GitHub登录。按终端提示处理；提交身份可以通过本仓库的`git config user.name`与`git config user.email`设置。

如果使用已经存在的项目，不要机械重复`git init`和添加origin；应在现有仓库内整合配置。该示例假定默认分支叫main，其他名称需要同时调整触发分支和部署条件。

### 3. 看一次执行记录

进入仓库的`Actions → CI and Pages deployment`，打开最新一次执行。预期顺序：

```text
获取代码 → 准备Node.js → 测试业务规则 → 构建
    → 本地产物冒烟 → 上传产物 → 部署Pages → 已发布页面冒烟
```

`deploy`任务里的`needs: build`表示：构建任务成功后才可以部署。每个步骤默认只在前面成功时继续；测试命令的非零退出码会让步骤失败。

部署成功后，可在部署记录的github-pages环境入口或仓库的Pages设置中查看站点地址。

GitHub配置部署的是build任务上传的同一份dist/产物，部署任务不重新构建，避免测试包与发布包不一致。

### 4. 通过PR看到一次真实的CI失败

1. 执行`git switch -c exercise/broken-threshold`。
2. 在`src/pricing.mjs`中把`totalCents >= 10_000`改成`totalCents > 10_000`，保留测试预期不变。
3. 提交修改并推送分支：`git add src/pricing.mjs`、`git commit -m "Exercise threshold regression"`、`git push -u origin exercise/broken-threshold`。
4. 在GitHub创建目标为main的Pull Request。打开Checks，预期100元边界用例失败，构建任务为红色。
5. 把`>`改回`>=`，提交并推送同一分支，观察检查重新运行并通过。

PR分支只执行检查，不部署。合并到main后会再检查一次，通过才部署。

**CI失败不会天然禁止合并。** 如果要强制拦截，需要在仓库的规则或分支保护中要求PR，并把`Test, build and check artifact`设置为必须通过的状态检查；可用选项取决于仓库权限和套餐。仅有这份YAML，失败会阻止本工作流部署，但仍可能允许有权限的人合并失败的PR。

### 5. 体验人工批准发布

在仓库`Settings → Environments → github-pages`配置`Required reviewers`。该能力是否可用取决于仓库可见性、套餐和组织设置。

设置生效后，main通过build，部署任务会等待有资格的审批人批准。审批后继续部署。需要自动发布时，再按团队规则取消这项审批要求。

## 五、读懂配置里的几个词

| 配置 | 含义 | 本示例 |
|---|---|---|
| workflow | 一条自动化工作流 | 一个YAML文件 |
| on | 什么事件触发 | main推送、指向main的PR、手动触发 |
| job | 一组在运行器上执行的任务 | build和deploy |
| runs-on / runner | 在什么机器上执行 | GitHub提供的Ubuntu运行器 |
| step | 任务内部按顺序执行的一步 | 测试、构建、上传等 |
| uses | 调用已有Action | 获取代码、准备Node、部署Pages |
| run | 执行命令 | npm test |
| needs | 指定任务依赖 | deploy依赖build成功 |
| if | 满足条件才执行 | PR不上传发布产物、不部署 |
| artifact | 本次运行生成并保存的产物 | 已测试的网页文件包 |
| environment | 部署目标与审批规则 | github-pages |

不用一次记住所有语法。先能回答：什么事件触发、运行哪些命令、失败停在哪里、成功发布到哪里。

本例无第三方依赖，因此没有安装依赖步骤。真实Node项目有package-lock.json时通常先执行`npm ci`；Java项目可能用Maven/Gradle，Python项目则按项目约定安装锁定依赖。工具不同，检查与发布之间的依赖关系相同。

## 六、这次验证了什么

2026-11-02已在本机Windows、Node.js v26.5.0及v24.22.1分别运行：

- 正常路径：15个业务测试通过，构建成功；dist/和release/各自通过4个资源HTTP检查、404检查、3个金额边界检查。
- 错误路径：隔离副本14个业务测试通过、1个失败；确认没有生成该副本的dist/或release/。
- JavaScript模块语法检查通过。

GitHub工作流配置使用Node.js 24，与本地复核的一个主版本一致。本机通过不能代替GitHub上的运行结果；本次未连接GitHub、未执行云端工作流、未发布远端站点。

本地冒烟检查使用临时HTTP服务并检查产物中的业务模块，不会启动真实浏览器。GitHub部署后的检查只验证页面可访问且包含预期表单标识；它不能证明浏览器按钮交互正确。页面实际输入操作、浏览器兼容性、移动端体验和完整端到端测试仍需要相应验证。

发布后冒烟失败会把GitHub任务标为失败，但页面此时已经部署，配置不包含自动回滚。真实生产项目需要另外设计回滚、监控和发布策略。
